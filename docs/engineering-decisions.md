# DeepResearch 工程取舍

本项目用于验证 DeepResearch 工作流、RAG 检索与可观测性方案，不以生产系统为目标。本文记录关键技术选型、替代方案与当前边界。

## 为什么使用 LangGraph

研究任务需要先规划，再动态分发多个子任务，最后汇总报告；前端还要显示每个节点的状态并回放历史。普通顺序循环实现更短，但分支状态和恢复点会散落在业务代码中。LangGraph 提供显式状态与 fan-out/fan-in，因此选用它承载工作流；FastAPI 只负责 HTTP/SSE 边界。

代价是框架概念和调试成本更高。若任务始终只有单条顺序链，直接使用 Python 状态机更合适。

## 为什么使用 SSE

研究过程主要是服务器单向推送进度，不需要浏览器持续向服务端发送消息。SSE 比 WebSocket 更容易接入 FastAPI 和浏览器重连机制。若以后需要人工在执行中修改计划，再评估 WebSocket 或双向事件协议。

## 为什么先做词法检索，再按需启用向量与重排

词法检索无外部模型依赖，适合作为本地开发和故障降级路径。配置 embedding 后使用混合评分；Cross-Encoder 只对候选集重排，避免对全部 chunk 推理。这样做的代价是当前内存实现仍需线性扫描，数据规模增大后应切换数据库索引并重新测量。

## 切块参数的含义

`1200` 字符和 `120` 字符重叠是中文/英文混合文档的保守默认值，不是最优结论。较小 chunk 有利于精确召回但会增加候选数量；较大 chunk 保留上下文但可能稀释关键词。正式使用时应基于版本化问答集比较 Recall@K、MRR、延迟和调用成本，再决定参数。

## 如何验证，而不是声称“生产可用”

- `python src/rag_eval_cli.py`：只验证排序和评测链路，内置 7-query 数据是 smoke set。
- `python src/rag_benchmark_cli.py`：在 100/1000/5000 个合成 chunk 上测量词法排序 p50/p95 延迟。结果依赖机器，只用于同环境回归。
- `pytest`、`alembic heads`、前端类型检查和构建：验证代码、迁移与界面集成。

当前评测仅覆盖离线检索链路和合成规模基准，不代表生产 QPS、SLA 或真实业务效果。
